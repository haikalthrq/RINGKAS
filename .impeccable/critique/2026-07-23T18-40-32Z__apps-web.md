## Overall Impression

The implementation has a trustworthy skeleton: answer, limitation, loading, and citation states are more mature than the surrounding information architecture. The single biggest opportunity is to make the full loop explicit: **question -> supported claim -> inspectable source -> next action**. Today the UI stops at a plausible answer and a list of sources rather than making verification feel decisive.

## Priority Issues

### [P1] The evidence loop can visually produce an uncited answer

**What:** `response.answer` renders whenever a response exists, even when `response.citations.length === 0`, at `apps/web/components/chat/chat-form.tsx:102,114-118`.

**Why it matters:** The product promise is that RINGKAS answers from BPS publications and always shows the proof. A substantive-looking answer beside “No source citations were returned” weakens that contract.

**Fix:** Gate substantive output behind usable citations. If none exist, replace the answer with “No verified answer available,” preserve the submitted question, and make every claim marker such as `[1]` map to a corresponding citation card with an inspectable source URL.

**Suggested command:** `/impeccable harden`

### [P1] Public orientation does not establish the corpus or primary action

**What:** Home says guest chat is available but gives no direct CTA, while the chat placeholder asks about Indonesia rather than DKI Jakarta, at `apps/web/src/app/page.tsx:2` and `apps/web/components/chat/chat-form.tsx:85`.

**Why it matters:** Users can infer a broader national corpus than the product currently supports and must find the actual first action through the header.

**Fix:** Make Chat the primary Home CTA, state “BPS DKI Jakarta publications” at the point of use, replace the national example, and align the entire public copy system with the intended language policy and `lang` attribute.

**Suggested command:** `/impeccable clarify`

### [P1] Document search stops at an unexplained first page

**What:** The request hard-codes `page=1&page_size=20` and displays `totalCount`, but renders no pagination or load-more control, at `apps/web/components/documents/document-search.tsx:42-45,72-85`.

**Why it matters:** A researcher can see “200 found” but access only the first 20, which makes the search promise incomplete.

**Fix:** Add next/previous or load-more behavior using `page`, `pageSize`, and `totalCount`. Put query/filter state in the URL, add clear filters, and preserve prior results when a subsequent request fails.

**Suggested command:** `/impeccable harden`

### [P1] Accessibility and error recovery are only partially implemented

**What:** Focus styling is explicit only for text inputs and textareas; links and buttons lack consistent `:focus-visible` treatment. Auth errors are not connected with `aria-describedby` or `aria-invalid`, and login disables native validation at `apps/web/src/app/(auth)/login/page.tsx:39-48`.

**Why it matters:** Keyboard and assistive-technology users receive inconsistent state feedback, while API errors can surface raw implementation details and entered content can disappear after failures.

**Fix:** Add a skip link, focus-visible styles for every interactive element, `aria-current="page"`, `aria-invalid`, and `aria-describedby`. Keep errors adjacent to their fields, map server errors to plain user-facing copy, preserve entered values, and increase small pills/source links to comfortable touch targets.

**Suggested command:** `/impeccable audit`

### [P2] Admin is a static debug panel rather than a confident operations flow

**What:** Job status is manually refreshed at `apps/web/src/app/(protected)/admin/page.tsx:58-69`, raw status values are shown directly, and the eight-field metadata block competes with logs and trigger controls.

**Why it matters:** Maintainers must interpret implementation status and manually poll, while operational detail overwhelms the primary trigger/status decision.

**Fix:** Use friendly status labels and a visible state sequence, show last-updated time, poll only while a job is active, prevent duplicate active jobs, validate `year_start <= year_end`, and put logs behind a “View recent logs” disclosure.

**Suggested command:** `/impeccable harden`

## Persona Red Flags

### Alex, Power User

Chat is short once Alex reaches `/chat`, but there are no shortcuts, recent questions, query history, follow-up context, or shareable search state. Search is capped at 20 visible results and has no pagination. There is also no visible sign-out/session control in `apps/web/components/site-header.tsx:19-27`.

### Jordan, First-Timer

Home explains the product indirectly but does not provide a clear “Ask a question” action. English copy, “indexed publications,” “source sufficiency,” and the national example require interpretation. There is no contextual explanation of what RINGKAS can and cannot answer.

### Sam, Accessibility-Dependent User

Semantic headings, labels, and live status regions are a good foundation. The main risks are missing focus styles for links/buttons, no `aria-current`, unassociated field errors, small pills/source links, and live regions that may announce too much result content.

### Nadia, BPS Researcher or Student

Nadia needs to move from question to proof quickly. Hidden DKI scope, missing visible source URL, no claim-to-citation mapping, and no shareable search state make verification slower than the product promise.

## Questions to Consider

1. Is Home actually a destination, or should `/chat` become the public landing surface?
2. If citation is the trust contract, should every answer claim visibly map to `[1]`, `[2]`, and an inspectable source URL?
3. Is DKI Jakarta the permanent corpus boundary, or should the public interface be designed for a broader BPS corpus now?
4. What is the minimum evidence condition under which RINGKAS must refuse to render an answer?
5. Would researchers value shareable query URLs and recent questions more than the current empty shell after submission?
6. Is Admin meant to be a one-shot ingestion trigger or an operations console? The current UI sits between both.
